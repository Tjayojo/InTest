**Status:** plan, rev 2. Nothing built yet.

**Spec:** `docs/superpowers/specs/2026-08-16-intest-api-test-generator-design.md` — §5, §18.

**Prerequisite:** base commit `2537fe3` on `main`. **656 passing — Architecture 6, Cli 410,
Runtime 205, Golden 35.** Measure it yourself; it moved more than twenty times during v1-e, and
`main` has other sessions on it.

**REQUIRED SUB-SKILL: `superpowers:subagent-driven-development`.** Each task is executed by a
fresh subagent and reviewed before the next begins.

InTest is a tool whose product is a CI gate. `README.md:113` tells adopters to run
`generate --check` in CI; `docs/getting-started.md` devotes Phase 8 to wiring it. The repository
has **no CI of its own** — `.github/` carries `ISSUE_TEMPLATE/` and `PULL_REQUEST_TEMPLATE.md`
(`SECURITY.md` is at the repo root), and no `workflows/` directory. Every verification during
v1-e was a human running `dotnet test` and reading four per-assembly counts by eye.

The repository is public and invites contributions through those templates. A contributor's pull
request currently receives no signal at all.

## Named decisions

### `[both-platforms]` — run the suite on Linux and Windows

`[lf-everywhere]` exists because line endings vary by platform, and v1-e Task 6 Step 5 could only
*simulate* the cross-platform case by toggling `core.autocrlf` on one machine. Real runners produce
the measurement acceptance could not.

`FixtureDocument`'s comment is the sharper argument: it says a Windows CI agent **cannot observe**
the platform list shrinking. Running only Windows reproduces the blind spot the code was written to
defend against.

The four predictions above are an argument *for* this decision, not against it — three latent
platform defects and one shipped `[paired]` defect, none of which any existing process would have
surfaced.

Rejected: macOS. It shares Unix filesystem semantics with Linux, so it adds cost without adding an
axis. Revisit on a macOS-specific report.

### `[pin-the-sdk]` — add `global.json`, pinned at 10.0.400

The concrete mechanism, not a general appeal to tidiness: `Directory.Build.props` sets
**`TreatWarningsAsErrors=true`** and **`LangVersion=latest`**. A runner image SDK bump turns any
newly-introduced analyzer warning into a build error, and silently changes the C# language version
the code compiles under. Real failure, real trigger.

**Pin at 10.0.400**, because §18's findings are stamped *"Measured on .NET SDK 10.0.400"* —
including *"`dotnet test` on the .NET 10 SDK still defaults to VSTest mode"*, which the entire
Golden harness depends on, since it parses `.trx`. Rev 1 said to pin at `net10.0`'s theoretical
minimum instead; that would pin to a band on which nothing was ever measured, and the
VSTest-versus-Microsoft.Testing-Platform default is exactly the kind of thing that moves within a
major. Choose a `rollForward` that keeps contributors unblocked — `latestFeature` or
`latestMinor`, not `disable` — and say which.

### `[fast-first]` — Golden runs on every pull request, in a parallel job. **Provisional.**

`CLAUDE.md` says Golden *"is the only suite that proves generated code both compiles **and** runs —
do not skip it when changing the template, the renderer, or the scaffold."* CI cannot classify
which pull requests those are, and a contributor cannot be relied on to say.

**Rev 1 claimed this default was "inherited rather than invented". That was wrong and is
withdrawn.** `CLAUDE.md`'s rule is about what a *given change* requires, not about what runs on
every PR. Treating it as a mandate for unconditional execution is an inference — a reasonable one,
since CI genuinely cannot classify PRs, but invented, and rev 1 called it inherited to make the
decision look better supported than it was.

Structure answers the cost objection without dropping coverage: Architecture + Cli + Runtime in one
job, Golden in a **separate parallel job**.

**Because §18's 3m30 was measured warm on a 22-processor machine, a 4-core hosted runner with a
cold NuGet cache — and Windows routinely ~2× Linux for .NET builds — makes ten to fifteen minutes
the expected case, not the pessimistic one.** So this decision is **provisional with a
pre-committed threshold**: if Golden exceeds **12 minutes wall clock on the slower platform**,
fall back to running it on a **merge queue** rather than every push to a PR branch. Pre-committing
the threshold and the fallback is what makes "change the decision, not the interpretation"
enforceable instead of aspirational.

Rejected: `paths-ignore` filtering. It reintroduces exactly the classification problem the decision
exists to avoid. Rejected: Golden on `main` only — it optimises the wrong thing, since the point is
catching a defect *before* it lands.

### `[dogfood]` — CI runs the generator against the three sample specs

**Rev 1's justification was invented and is withdrawn** — there is no committed generated output
for staleness to accumulate in, and CI cannot use the adopter shape (`dotnet tool restore` +
`dotnet intest`) because nothing is published.

The real and sufficient justification: **the three sample specs are the only real-world-shaped,
hand-authored, multi-producer OpenAPI documents in the repository, and no automated test runs the
generator against any of them.** `InTest.Golden.Tests` uses `Specs/orders.json`,
`Specs/hostile-text.json` and inline string specs, and touches `samples/` nowhere.
`CliExitCodeTests.CheckFlagIsWiredThroughToGenerate` already exercises the
init → generate → `--check` → mutate → `--check` shape through the real CLI, but on a trivial
inline spec. The new coverage is the documents, not the flow — and it costs about five seconds.

**Scope limit, decided:** this job must not require a running API. `generate` and `--check` are
static. Starting the samples over real HTTP needs the environment setup `samples/README.md`
documents, where getting it wrong produces 500s and silent 404s rather than an obvious failure.
That belongs in a separate job if it is built at all; putting it here makes the most-run job the
most fragile.

### `[pin-actions-by-sha]` — third-party actions inherit the dependency policy

`CONTRIBUTING.md`'s dependency policy is hard. It was written about NuGet packages, but an action
executes where it can read repository secrets, which is a strictly larger supply-chain surface.

Pin every third-party action by **commit SHA**, not tag — a tag is mutable and can be repointed
after review. **Rev 1 stated this and then scheduled no task that did it.** Every task that writes
a workflow file now carries the requirement explicitly.

### `[publish-before-release-machinery]` — the release job is deferred, not planned here

Rev 1 included a release workflow. It is removed, for three reasons that compound:

1. It cannot release. No IDs are reserved, the API key is the owner's, and the job would be
   forbidden from its own purpose.
2. Its version-source step was wrong. `InitCommand.cs:227` **hardcodes**
   `<PackageReference Include="InTest.Runtime" Version="0.1.0" />`, so packing from a tag at
   `1.2.3` yields a CLI that scaffolds a reference to a runtime version it did not publish.
   `CLAUDE.md` records that package versions are duplicated in three places by design and must
   move together; `CliVersion.Current` is a fourth consumer, and it feeds `intestVersion` and
   therefore `--check`'s `[exact-match]` gate. **A version bump is a source change, not a
   pack-time flag** — the only available direction is verifying the tag against the source.
3. Machinery with no consumer rots before first use.

Publishing `0.1.0` is an owner-afternoon task that unblocks four things at once: `dotnet tool
restore` from a bare clone, F13's `dotnet intest` invocation, `[dogfood]` running in the shape it
would like to claim, and a release job having something real to verify against. §18 records all
four IDs as free on nuget.org — **a fact with a shelf life, on a now-public repository.**

The honest order is: build CI, publish, then build release machinery around a published baseline.

## Self-review

**Rev 1's real failure was not any single false statement — it was confidence distributed
unevenly.** The things it checked, it checked properly. The things it did not check, it wrote in
the same voice. A reader could not tell the two apart, which is why the "verified" section is now
split into measurements and predictions.

**Where a reviewer should push now.** `[fast-first]` still decides before Task 1 Step 3 measures,
and the honest defence is no longer "the default is inherited" but "a threshold and a fallback are
pre-committed, so the measurement can overturn it without renegotiation." Judge whether 12 minutes
is the right number — it is chosen, not derived, and it is the weakest quantity in this document.

**`[dogfood]` is now justified by a much narrower claim** — three unexercised documents, five
seconds of CI. That is a real gap but a small one. If a reviewer thinks it is not worth a workflow,
that is a reasonable position and Task 4 Step 3 is already gated on it.

**What this plan does not do.** It does not close the Phase 8 gap, and unlike rev 1 it does not
build machinery that pretends to. `dotnet tool restore` still cannot resolve `intest.cli` from a
bare clone. That remains the top open item in `docs/v0-acceptance.md`, it is blocked on an owner
decision rather than on engineering, and `[publish-before-release-machinery]` argues it should
happen before any release workflow is written.
