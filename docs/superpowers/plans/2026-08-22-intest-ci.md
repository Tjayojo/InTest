# InTest CI

**Status:** plan, rev 1. Nothing built yet.

InTest is a tool whose product is a CI gate. `README.md:113` tells adopters to run
`generate --check` in CI; `docs/getting-started.md` devotes Phase 8 to wiring it. The repository
has **no CI of its own** — `.github/` carries issue templates, a PR template and `SECURITY.md`,
and no `workflows/` directory. Every verification during v1-e was a human running `dotnet test`
and reading four per-assembly counts by eye.

The repository is public and invites contributions through those templates. A contributor's pull
request currently receives no signal at all.

---

## What was verified before writing this

Stated so a reviewer can attack the evidence rather than the conclusion. Each was run, not read.

- **No `global.json`.** The SDK floats to whatever a runner provides. The repo pins package
  versions centrally (`Directory.Packages.props`), pins its own `Version`, and scaffolds a pinned
  tool manifest for adopters — an unpinned SDK is the one loose pin in a project whose entire
  discipline is pinning.
- **The suite is platform-clean on the axis that matters.** `FixtureDocument` deliberately unions
  an explicit invalid-character set with `Path.GetInvalidFileNameChars()`, and its doc comment
  names this exact scenario: *"a Windows dev box or CI agent cannot observe this list shrinking —
  only a direct assertion on the list itself can."* `\` is in the explicit set, so
  `ReportsAnOperationKeyThatCannotBeAFileName`'s backslash row does not depend on Windows
  filesystem rules. No `OSPlatform` guards and no `.exe` literals anywhere in `src/` or `tests/`.
- **`InTest.Golden.Tests` is hermetic with respect to the package cache.** It passed 35/35 with
  `~/.nuget/packages/intest.*` deleted, so it never resolves the packages under test from a
  machine-wide cache.
- **`InitCommandTests` spawns real `git`.** Hardened during v1-e Task 2 — `GIT_CONFIG_GLOBAL` and
  `GIT_CONFIG_SYSTEM` redirected to an empty file, `GIT_TERMINAL_PROMPT=0`, a timeout, and
  concurrent stream reads. It needs `git` on `PATH`; GitHub runners provide it.
- **Current state:** 656 passing, 0 failing — Architecture 6, Cli 410, Runtime 205, Golden 35.

**Not verified, and the plan must not assume it:** how long the Golden suite takes on a cold CI
runner. Local wall-clock readings are single measurements of an unstable quantity and §18 already
records that a total is not comparable to another without a per-class breakdown *and* repetition.
Task 1 measures it rather than guessing.

## Named decisions

### `[both-platforms]` — run the suite on Linux and Windows

Not a nice-to-have. `[lf-everywhere]` exists because line endings vary by platform, and v1-e Task 6
Step 5 could only *simulate* the cross-platform case by toggling `core.autocrlf` on one machine.
A Linux runner and a Windows runner produce the real measurement that acceptance could not.

`FixtureDocument`'s comment is the sharper argument: it says a Windows CI agent **cannot observe**
the platform list shrinking. Running only Windows would reproduce exactly the blind spot the code
was written to defend against.

Rejected: macOS as well. It shares Unix filesystem semantics with Linux, so it adds cost without
adding an axis. Revisit if an adopter reports a macOS-specific defect.

### `[pin-the-sdk]` — add `global.json`

Without it, a runner image upgrade changes the compiler under the project silently, and a green
run stops being evidence about the code. `rollForward` must be chosen deliberately, not defaulted:
too strict breaks CI the day the image moves, too loose reintroduces the drift. Decide and record.

This also fixes a real inconsistency — the repo pins everything else and tells adopters to pin.

### `[fast-first]` — Golden runs on every pull request, in parallel with the fast suites

This is the one genuine cost decision, and it is decided rather than deferred.

`CLAUDE.md` is explicit: Golden *"is the only suite that proves generated code both compiles **and**
runs — do not skip it when changing the template, the renderer, or the scaffold."* CI cannot know
which pull requests those are, and a contributor cannot be relied on to say. A regression in
generated code that reaches `main` before anything notices is precisely the failure CI exists to
prevent, and it is the failure that would most damage a tool whose product is generated code.

The cost objection is answered by structure rather than by dropping coverage: run Architecture,
Cli and Runtime as one job and Golden as a **separate parallel job**. Fast feedback still arrives
in roughly a minute; Golden lands when it lands. Nobody waits on it to learn that a typo broke the
build.

Rejected: Golden on `main` only. It optimises the wrong thing — the whole point is to catch a
defect *before* it is on `main`.

### `[dogfood]` — CI runs `generate --check` against the repository's own sample APIs

InTest has four sample APIs in-repo. A job that generates against them and runs `generate --check`
proves the shipped gate works, in the shape an adopter uses it, on both platforms.

It is also the only mechanism that would catch a template or renderer change that is internally
consistent — one that updates the golden file and the generated output together, so
`OutputMatchesTheGoldenFile` passes while the *committed* output of a real project goes stale.

**Scope limit, decided:** this job must not require a running API. `generate` and `--check` are
static — they read a spec and write files. Starting the samples over real HTTP needs the
environment-variable setup `samples/README.md` documents, where getting it wrong produces 500s and
silent 404s rather than an obvious failure. That belongs in a later, separate job if it is built
at all; putting it here would make the most-run job the most fragile.

### `[pin-actions-by-sha]` — third-party actions are dependencies and inherit the dependency policy

`CONTRIBUTING.md`'s dependency policy is hard — no preview/prerelease, permissive licences only,
check deprecation and vulnerability metadata. It was written about NuGet packages, but a GitHub
Action executes in a context that can read repository secrets, which makes an unpinned action a
strictly larger supply-chain surface than a NuGet package.

Pin every third-party action by **commit SHA**, not by tag: a tag is mutable and can be repointed
after review. Extend the dependency-policy section to say so, so the rule lives where the other
dependency rules live rather than only in a workflow file.

### `[release-is-a-tag]` — publishing happens from CI, on a tag, never from a laptop

Publishing `0.1.0` by hand from a developer machine is how the stale-package-cache hazard arose
twice, and that hazard was only closed for *testing* by `scripts/local-e2e-test.ps1`. Releasing by
hand leaves the same shape open: local state, in play, at the moment bytes become permanent.

A release job packs from a clean checkout of a tagged commit, with the suite green as a
precondition, and publishes. NuGet package metadata is immutable once published, so this job is
worth more care than the others.

**Not in this plan's scope to run.** The IDs are not reserved and the owner controls the API key.
Task 4 builds and proves the job as far as it can go without publishing, and says explicitly what
was therefore not exercised — the same discipline v1-e Task 6 Step 1 applied to
`dotnet tool restore`.

## Tasks

### Task 1: Measure, then pin

- [ ] **Step 1:** Determine the SDK version CI should pin. Establish what the project actually
      requires rather than copying the developer machine's `10.0.400` — check `net10.0`'s minimum
      and whether anything in the build depends on a feature newer than that. Add `global.json`
      with a deliberate `rollForward`, and say why that value.
- [ ] **Step 2:** Measure the Golden suite on a real runner, both platforms, **with a per-class
      breakdown and more than one run**. §18 records that a bare wall-clock total is not
      comparable to another without both. This number decides nothing in `[fast-first]` — that is
      already decided — but it is what a future reviewer needs to revisit it honestly.
- [ ] **Step 3:** Confirm the full suite passes on Linux. This has never been run. Expect failures
      and report them as findings rather than working around them; a test that assumes Windows is
      a defect this plan exists to surface.

### Task 2: Build and test workflow

- [ ] **Step 1:** On `push` to `main` and on `pull_request`. Matrix over Linux and Windows per
      `[both-platforms]`.
- [ ] **Step 2:** Two parallel jobs per `[fast-first]` — Architecture + Cli + Runtime in one,
      Golden in the other.
- [ ] **Step 3: Assert per-assembly counts, not just green.** A dropped test suite still passes.
      This is a recorded defect on this project, not a hypothetical. Decide the mechanism — the
      honest options are a floor per assembly, or failing on any decrease — and note that a strict
      equality check makes every legitimate test addition a two-place edit. Pick one and say why.
- [ ] **Step 4:** Cache NuGet packages deliberately or not at all. If cached, the key must include
      `Directory.Packages.props` so a version change cannot resolve against a stale restore —
      this repo has already been bitten twice by exactly that class of staleness.

### Task 3: Dogfood workflow

- [ ] **Step 1:** Generate against each sample spec and run `generate --check`. Exit 0 required.
- [ ] **Step 2:** Prove the job can fail. Edit a sample spec without regenerating and confirm the
      job goes red naming the file. A dogfood job that cannot fail is decoration — and this
      project's recurring defect is exactly a check that passes while asserting nothing.
- [ ] **Step 3:** Confirm no fixture drift and that nothing is left modified in the working tree.
      `generate` writes; the job must not silently commit or leave dirt.

### Task 4: Release workflow

- [ ] **Step 1:** Tag-triggered. Packs both projects from a clean checkout, suite green as a
      precondition, `THIRD-PARTY-NOTICES.md` included in the package.
- [ ] **Step 2:** Verify the produced `.nupkg` metadata — `RepositoryUrl`, `PackageProjectUrl`,
      `Authors`, `Copyright`, licence — matches what `Directory.Build.props` sets. It is immutable
      after publish.
- [ ] **Step 3:** **Do not publish.** No IDs are reserved and the API key is the owner's. Build the
      job, prove every step that can be proven without uploading, and **record precisely which step
      was not exercised** — the same discipline v1-e Task 6 Step 1 applied when `dotnet tool
      restore` could not run.
- [ ] **Step 4:** The version comes from the tag, or the tag is verified against
      `Directory.Build.props`. A release whose tag and package version disagree is unfixable after
      upload. Decide which direction and enforce it in the job.

### Task 5: Documentation

- [ ] **Step 1:** `CONTRIBUTING.md` — what CI runs, what a contributor should expect on a pull
      request, and the `[pin-actions-by-sha]` rule inside the existing dependency policy.
- [ ] **Step 2:** `CLAUDE.md` Commands section, and a badge in `README.md` only once the workflow
      has actually run green — a badge is a claim, and stale claims are this project's named
      recurring defect.
- [ ] **Step 3:** Record in the spec that InTest gates itself with `generate --check`, and note it
      is the strongest available evidence the gate works.

## Self-review

**Where a reviewer should push.**

`[fast-first]` is the decision most likely to be wrong, and it is wrong in a way that will not show
up for months: if Golden turns out to take fifteen minutes on a cold runner rather than three,
"parallel job" stops being an answer and contributors start waiting. Task 1 Step 2 measures it, but
the decision is made *before* the measurement, which is the shape of reasoning that produced
`[major-only]` in the v1-e plan and had to be retracted. The mitigating difference: `CLAUDE.md`
already states Golden must not be skipped for template, renderer or scaffold changes, so the
default is inherited rather than invented. If the measurement is bad, the honest response is to
change the decision, not to reinterpret the measurement.

`[dogfood]` may overlap `InTest.Golden.Tests` more than this plan admits. Both generate and compare.
The stated distinction — that Golden updates its own expected output while the sample projects hold
*committed* output — needs testing rather than asserting. If it turns out Golden already covers it,
the job is cost without coverage and should be cut.

**What this plan does not do.** It does not close the Phase 8 gap: `dotnet tool restore` still
cannot resolve `intest.cli` from a bare clone, because nothing is published. `[release-is-a-tag]`
builds the machinery that would close it, and stops short of the upload. That remains the top open
item in `docs/v0-acceptance.md` and this plan should not be read as addressing it.
